1. PROJECT MISSION
Build a complete, professional Android application named El Ghassala (

‫ )الغّس الة‬from scratch.

El Ghassala is an offline-first financial and transportation expense management application. Its main
purpose is to help users organize shared transportation costs, daily expenses, money transfers,
participant balances, driver refunds, settlements, saved routes, and financial reports in one simple and
reliable place.
This is not a request to create a basic prototype or a visually attractive mockup. The objective is to deliver
a fully functional, stable, polished, production-quality Android application.
The application must combine three essential qualities:
1. Professional functionality: Every feature must work correctly, with reliable calculations and persistent
data.
2. Exceptional usability: The application must be understandable and comfortable even for users with
limited technical experience.
3. Outstanding visual quality: The interface should feel modern, premium, polished, visually impressive,
and thoughtfully designed.

7. DAY MANAGEMENT
The application must organize financial activity into individual days. Users should be able to:
Create a new day.
Give the day a custom title.
Select or record its date.
Add participants.
View all transactions associated with that day.
Edit day information.
View a complete day summary.
Close a day.

Each day must have a clear financial status. Closing a day should not delete or hide its financial

The person or people who paid the driver.

Additional notes.

CRITICAL FINANCIAL CALCULATION EXAMPLE (MANDATORY ACCEPTANCE TEST)

Scenario:
Ahmed and Hima used the same transportation.
The fare per person is 10 EGP.
Expected total cost is 20 EGP.
Ahmed paid the driver 20 EGP.
Hima also paid the driver 10 EGP.
The actual amount collected by the driver is 30 EGP.
Required Outcome:
Expected transportation cost = 20 EGP.
Actual amount paid = 30 EGP.
The driver owes Ahmed 10 EGP.
Hima has no outstanding transportation payment.
The additional 10 EGP must not disappear from financial calculations.
The application must recognize this as a driver refund situation, not incorrectly mark everything as
settled. This example is an essential acceptance test.

9. DRIVER REFUND MANAGEMENT
Create a reliable system for tracking money owed by drivers to participants. Whenever a transportation
transaction creates an overpayment, the application must preserve the refund as a separate financial
record.
The user should receive a clear confirmation prompt asking whether the refund has actually been
received. Possible outcomes:
Yes: Mark the refund as collected.
No: Keep the refund outstanding.
Dismiss or go back: Preserve the outstanding refund without marking it as collected.
Requirements: Track refunds independently for each participant; support multiple participants receiving
refunds from the same transaction; store the refund amount, collection status, and collection date when
applicable; preserve historical refund information; allow users to review outstanding and collected
refunds; reflect refund status correctly in statistics, reports, backups, and exports. Never assume that a
refund has been received simply because the transportation transaction was saved.

11. TRANSFERS
Create a separate section for recording money transfers between participants. Users should be able to:
Select the sender, Select the receiver, Enter the transfer amount, Add a date and time, Add optional notes,
Review transfer history, Edit or delete a transfer with appropriate confirmation.
Transfers must affect participant balances correctly.
Important: Transfers are not expenses. Never include transfers in actual spending totals, transportation
expense totals, cash expense totals, or average spending calculations. They must remain a separate
financial movement category.

12. SMART SETTLEMENT CENTER
Build a central settlement system that calculates financial balances across all relevant open days. The
Settlement Center should provide: Total outstanding balances, Amounts owed to the current user,
Amounts the current user owes, Participant balance summaries, Outstanding driver refunds, Collected
driver refunds, Suggested settlements, and Detailed participant ledgers.

Smart Settlement Suggestions
Create a debt simplification mechanism that reduces unnecessary individual payments. For example, if
several participants owe money to each other, the system should calculate a smaller and clearer set of
settlement transactions. The system should suggest practical payments without changing historical
records automatically. Users must explicitly confirm when they record a settlement.

People Balances
Provide a clear list of participants and their current net balances. Each person should have a detailed
ledger showing: Transportation obligations, Cash expense contributions, Transfers sent, Transfers
received, Settlements, Outstanding refunds, Collected refunds, and Current net balance.

Important Rules
Closed days must be handled according to a consistent settlement policy.
Driver refunds must remain separate from participant-to-participant debts.
Transfers must affect balances but must not increase spending totals.
Settlement records must not be counted as new expenses.
Avoid double-counting transactions.

13. SAVED ROUTES
Create a dedicated Saved Routes feature. Users should be able to save frequently used transportation
routes. Each saved route should contain: Route name, Origin, Destination, Default fare, Usage count,
Creation date, and Last update date.
Users should be able to: Add routes, Edit routes, Delete routes with confirmation, Search routes, Sort by
most frequently used, Sort by recently used, and Start a transportation transaction directly from a saved
route.
When a route is selected, prefill Origin, Destination, and Default fare. All fields must remain editable.
Selecting a saved route must never reuse previous participants, payments, or transaction details. It must
not automatically create a transportation transaction. Provide an optional action to save a newly entered
route for future use when recording transportation. Prevent accidental duplicate routes through sensible
duplicate detection.

14. PEOPLE MANAGEMENT
Create a dedicated participant management feature. Users should be able to: Add a person, Edit a
person's information, View a person's financial summary, View their transaction history, View their current
balance, Review their transportation activity, Review their cash expense activity, Review transfers, Review
driver refunds, and Search participants.
Prevent accidental duplicate people. Use stable internal person identifiers rather than relying only on
display names. When a person is renamed, historical transactions must remain correctly associated with
that person. Do not silently delete a participant who is referenced by historical financial records. If deletion
is supported, provide a safe archival or deactivation approach that preserves financial history.

volume separately, Outstanding driver refunds, Collected driver refunds, Average daily spending,
Comparison with the previous equivalent period, Spending trends, Expense category distribution, Daily and

Provide appropriate charts, graphs, and visual summaries. Do not use misleading charts or combine

17. BACKUP AND RESTORE
Create a reliable local backup and restoration system. Users must be able to export their application data
into a portable backup file and restore it later.
The backup should include all essential information: Days, Participants, Transactions, Driver refunds,
Saved routes, People information, Relevant settings where appropriate, and Any additional data necessary
to reconstruct the application state.
Requirements: Use a versioned backup format; validate backup files before importing; handle older
backup formats safely; preserve relationships between database records; avoid duplicate imports; provide
clear confirmation before replacing or merging existing data; handle corrupted or incomplete backups
gracefully; never silently overwrite important user information; provide clear success and failure
messages.
The backup system must work offline. Do not introduce mandatory cloud storage or account-based
synchronization.

22. DATABASE AND ARCHITECTURE REQUIREMENTS
Design a clean database schema that supports the complete application. The data model should
represent, at minimum: Days, People, Transactions, Driver refunds, Saved routes, and Any additional
entities required for settlement or application settings.
Use stable primary keys and proper relationships. Use database transactions for operations that modify
multiple related records. Use explicit, tested database migrations. Never use destructive database resets
as a shortcut.
Keep financial calculations in dedicated domain or utility logic rather than scattering formulas throughout
UI screens. Separate: UI, ViewModels, Domain logic, Repositories, Database entities, DAOs, Backup and
export services.
